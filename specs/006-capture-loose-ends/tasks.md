- [X] T002 [US2] **Answered, on an OBSBOT Tiny 2 Lite at 1280x720.** The camera sustains the rate — it offers ~30.2 buffers/s — and the consumer was never the problem (`queue_full=0` in every run). The shortfall was ours: `rate_limited=19` of 319 offered, delivering 28.5fps. `cargo run -p elementium-media --example capture_attribution` is the measurement, and it tries each source in turn because this machine enumerates a virtual V4L2 node ahead of the real camera that negotiates and then delivers nothing — taking the first source measured a camera that does not exist. Original task follows. Run a camera for 12 seconds at 30fps and read the capture counters; attribute the missing frames to the camera, the rate limiter, or the consumer
- [X] T003 [US2] **Fixed: 28.5fps → 30.0fps.** The limiter measured its interval from the last *accepted* frame, which ratchets: a frame arriving late moves the window late with it, so the next one — arriving on the camera's own cadence — is early and gets dropped, moving the window again. It now advances a deadline by exactly the nominal interval, keeping the reference fixed, and allows a frame an eighth of an interval early so jitter costs nothing. Measured across three runs each: 28.5fps (19 dropped of 319) → 29.6-29.8 (5-9 of 305-309) with the fixed timeline → **29.9-30.0 (1-3 of 301-303)** with the tolerance as well.
- [~] T006 **Instrumented and measured 2026-08-08; driver-side truncation strongly indicated, not yet proven.** Failures are not the tail of the normal size distribution but a separate population: successful buffers bottom out around 186,887-192,204 bytes against a ~203 kB mean (measured over 1,200 frames in one run, with zero failures in that run), while the five failures captured in other runs were 3,970 / 32,611 / 32,687 / 32,714 / 65,255 bytes — an order of magnitude below the floor. Four of five had no SOI marker; one had a genuine trailing EOI but no SOI. Head and tail bytes are high-entropy, so the buffers are neither zeroed nor stale-but-recognisable. **Killed by measurement**: the hypothesis that a nonzero `chunk().offset()` meant we read from the wrong place — it is 0 on both clean decodes and failures, and that diagnostic was removed once it had done its job. The remaining reading is a UVC/USB transfer that loses its leading packets, which carry SOI, while trailing ones arrive; that is a driver-committed incomplete buffer rather than a race in our read, and our copy already takes exactly `chunk().size()` bytes from offset 0 in one pass before decoding. **Not yet proven**: the five failing buffers were observed by one measurement run and not reproduced since (1,200 frames, 0 failures), so the SOI pattern rests on five samples. No fix, because a driver-side truncation is not ours to fix. **The open question is answered**: such buffers are logged in full three times per stream and counted thereafter, since the diagnostic is identical after the first couple and the periodic `capture decode cost` line already carries the rate. Silently dropping them would have hidden the only evidence there is. [US2] **~0.5% of MJPEG buffers fail to decode**, and they are *short* rather than corrupt: `mjpeg_decode_failed len=32656` against a mean source buffer of 202kB. One or two per 300 frames, which is the whole of the residual gap now that the limiter is fixed. Whether the camera emits a truncated buffer or we snapshot one mid-write is not established — the capture path already copies the mapped buffer before decoding precisely because the driver writes into it, so a race there is the obvious suspect and the buffer length is the evidence to start from
