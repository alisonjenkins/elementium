- [ ] T020 [US1] **The frame the browser receives is not the frame we send.** Our encryption is *correct*: an encrypted frame taken straight from the encoder decrypts cleanly when run through livekit's own worker functions and key derivation — `findSliceNALUUnencryptedBytes` agrees on 27, `parseRbsp` recovers exactly 1531+12+2, the trailer reads `[12, 0]`, and AES-GCM returns the original 1515 bytes. In a real call the same worker reports `InvalidKey: Decryption failed` on every frame. So the bytes change between our writer and the browser's transform, and the failure is transport, not framing. str0m's packetiser does not trim trailing zeros, so the next suspects are the SFU and Chrome's depacketiser. **Trailing zero ruled out**: publishing at key index 1, so the trailer's last byte is non-zero, fails exactly as index 0 does. The publisher takes `--key-index` and the test is kept (as `fixme`) because the question recurs. **Also ruled out**: the payload type's packetization mode, the SFU's codec registration, str0m trimming trailing zeros (it does not), and livekit's codec detection. **Resolved: frames are not assembled, so this is packetisation, not decryption.** A run with the page holding *no* key — and therefore no livekit transform at all — still reports `framesReceived: 0`, and a later run with the key reported no decryption errors. The single `InvalidKey` observation was not reproducible and should not have been treated as a fact. **Also ruled out by reading the code rather than assuming it**: our encrypt already RBSP-escapes the ciphertext, IV and trailer *together*, exactly as livekit does — so the counter-shaped IV, which really does contain `00 00 01` for small counters, is escaped and cannot introduce a spurious start code. **Answered: it is our bug.** Two browsers carry H.264 under E2EE through the same SFU without trouble — 459 packets, 161 frames received, 161 decoded, none dropped. So the stack supports it and something about *our* encrypted H.264 specifically does not survive. That also gives the investigation what it has lacked throughout: a working reference to diff against. The remaining difference on the sending side is str0m's packetiser rather than libwebrtc's, on a frame whose slice NAL is opaque after the first two bytes. **Fragmentation ruled out too**: publishing at 160x120, small enough that frames travel in a single RTP packet, fails exactly as 320x240 does. So a complete NAL in one packet with the marker set still assembles nothing, which is a very tight constraint — the packets are well-formed enough for the SFU to forward 200 of them and for the receiver to count them. **The SFU is innocent too.** Its own stats for our encrypted H.264 track read `frames: 352, keyFrames: 2, packetsLost: 0, packetsOutOfOrder: 0` — it parses our stream correctly, counts frames by marker, finds the keyframes, and forwards everything. So the packets are well-formed by its reckoning and the fault is in Chrome's depacketiser, on a stream the same Chrome handles when libwebrtc packetised it. **Also checked**: our encoder writes `slice_type` 2 and 0, the short forms, so `first_mb_in_slice`, `slice_type` and `pic_parameter_set_id` all fit inside the first byte of the slice header and stay in the clear — a depacketiser that needs the PPS id can still read it. A pass-through probe transform in the page recorded nothing and was removed rather than left in as a broken instrument — attaching a second transform to a receiver needs more care than one line. Earlier framing follows. **Our H.264 E2EE framing disagrees with livekit'"'"'s worker.** Localised by two controls that now live beside the test: VP8 with the same encryption assembles and decodes 204/204, and *plain* H.264 through the same path assembles 210 and decodes 209. Only H.264 **and** encryption fails, and the encrypted frame carries the same Annex B NAL structure (7,8,5) as the plain one — so it is not packetisation, not the video publish path, and not the decoder. The contract in `spec.md` was read from livekit's source and checked against 596 of their frames; something in it disagrees with the shipped worker, and the RBSP escaping is the part least likely to be right. Blocks T016. Earlier framing follows. **Our H.264 RTP never assembles into a frame at the receiver.** With the codec declared correctly the SFU registers `video/H264` at the right size and forwards it — the browser counts `packetsReceived` climbing past 200 — but `framesReceived` stays at 0 and `pliCount` rises, so it is asking for a keyframe it never gets. Not the E2EE keys: livekit's worker reports no errors. Not the decoder: nothing reaches it. That leaves our packetisation of the encrypted Annex B, which VP8 does not exercise because its framing differs. Blocks T016
