- [X] T020 [US1] **RESOLVED 2026-08-09: the PPS id was inside the ciphertext.** Chromium parses `first_mb_in_slice`, `slice_type` and `pic_parameter_set_id` out of every IDR slice before it decrypts anything, looks the PPS up by that id, and drops the frame when it finds none (`h264_sps_pps_tracker.cc: No PPS with id << 1 received`); every delta frame is then withheld behind the sequence gap the dropped keyframe left. livekit leaves two bytes of the frame in the clear, and our driver wrote `slice_type` 7 -- ue(v) seven bits -- so with one bit of `first_mb_in_slice` the id began at bit eight, the first ciphertext byte. Chromium's own encoder writes `slice_type` 2, three bits, which is why browser-to-browser worked under the identical scheme. The fix rewrites the IDR slice header to `slice_type` 2 and gives the four freed bits to `idr_pic_id`, so the header keeps its exact bit length and the entropy-coded slice data does not move (`crates/elementium-codec/src/vaapi/slice_header.rs`). Measured against Chromium through the SFU: 201 frames received, 201 decoded, 0 dropped, 0 PLIs -- the plain control exactly, where it had been 0 frames and 39 PLIs. **Two things had to be fixed before the measurement meant anything.** First, the browser tests never rebuilt the publisher they drive, so a run measured whatever binary was in `target/debug/examples`; that is what made the earlier SPS VUI change read as "did not work" and made a clear-header diagnostic appear to change nothing. Second, `framesReceived` was read throughout as evidence about assembly, but an insertable-streams transform sits between the depacketiser and that counter, so under E2EE "failed to assemble" and "failed to decrypt" are the same observation -- and a receiver merely lacking the key does not separate them, because livekit still installs the transform. A receiver with no key at all builds a plain `Room` with no transform, and that run is what exonerated decryption. libwebrtc reports why it discards a packet only through RTC_LOG: `ELEMENTIUM_WEBRTC_LOG=1` turns those on and named the fault in one run. **Refuted along the way, and recorded so they are not re-tried**: the ciphertext-start-code theory (`h264_encrypted_start_codes.rs`), the SPS VUI rewrite theory (the VUI is still written, and is correct, but was not the cause), and "Incorrect StapA packet" (logged at teardown, and the aggregation packets are well-formed both plain and encrypted -- see `h264_stap_a_validity.rs` and `h264_real_encoder_stap_a.rs`). Original investigation follows.  Our encryption is *correct*: an encrypted frame taken straight from the encoder decrypts cleanly when run through livekit's own worker functions and key derivation — `findSliceNALUUnencryptedBytes` agrees on 27, `parseRbsp` recovers exactly 1531+12+2, the trailer reads `[12, 0]`, and AES-GCM returns the original 1515 bytes. In a real call the same worker reports `InvalidKey: Decryption failed` on every frame. So the bytes change between our writer and the browser's transform, and the failure is transport, not framing. str0m's packetiser does not trim trailing zeros, so the next suspects are the SFU and Chrome's depacketiser. **Trailing zero ruled out**: publishing at key index 1, so the trailer's last byte is non-zero, fails exactly as index 0 does. The publisher takes `--key-index` and the test is kept (as `fixme`) because the question recurs. **Also ruled out**: the payload type's packetization mode, the SFU's codec registration, str0m trimming trailing zeros (it does not), and livekit's codec detection. **Resolved: frames are not assembled, so this is packetisation, not decryption.** A run with the page holding *no* key — and therefore no livekit transform at all — still reports `framesReceived: 0`, and a later run with the key reported no decryption errors. The single `InvalidKey` observation was not reproducible and should not have been treated as a fact. **Also ruled out by reading the code rather than assuming it**: our encrypt already RBSP-escapes the ciphertext, IV and trailer *together*, exactly as livekit does — so the counter-shaped IV, which really does contain `00 00 01` for small counters, is escaped and cannot introduce a spurious start code. **Answered: it is our bug.** Two browsers carry H.264 under E2EE through the same SFU without trouble — 459 packets, 161 frames received, 161 decoded, none dropped. So the stack supports it and something about *our* encrypted H.264 specifically does not survive. That also gives the investigation what it has lacked throughout: a working reference to diff against. The remaining difference on the sending side is str0m's packetiser rather than libwebrtc's, on a frame whose slice NAL is opaque after the first two bytes. **Fragmentation ruled out too**: publishing at 160x120, small enough that frames travel in a single RTP packet, fails exactly as 320x240 does. So a complete NAL in one packet with the marker set still assembles nothing, which is a very tight constraint — the packets are well-formed enough for the SFU to forward 200 of them and for the receiver to count them. **The SFU is innocent too.** Its own stats for our encrypted H.264 track read `frames: 352, keyFrames: 2, packetsLost: 0, packetsOutOfOrder: 0` — it parses our stream correctly, counts frames by marker, finds the keyframes, and forwards everything. So the packets are well-formed by its reckoning and the fault is in Chrome's depacketiser, on a stream the same Chrome handles when libwebrtc packetised it. **Our own stack does the whole round trip.** `encrypted_h264_survives_our_own_publish_subscribe_round_trip` publishes encrypted H.264 through the real SFU and subscribes with our own client: the picture arrives decoded, zero inbound E2EE drops. The stream is self-consistent — our packetisation, encryption, the SFU's forwarding, our depacketisation and our decode all agree — so the disagreement is specifically with Chrome's depacketiser. **That makes the shippable position clear**: H.264 under E2EE works Elementium-to-Elementium and browser-to-browser, but not Elementium-to-browser. Preferring VP8 for *publishing* whenever E2EE is on is the safe default; H.264 stays for receiving, where the hardware decoder earns its keep, and for unencrypted publishing. **Re-checked 2026-08-08 after today's codec changes**: `encrypted_h264_survives_our_own_publish_subscribe_round_trip` and `audio_survives_real_publish_subscribe_round_trip` both still pass against the live SFU (`cargo test -p elementium-webrtc --test livekit_local_roundtrip -- --ignored`), so the odd-geometry chroma fix and the even-dimension crop did not disturb the encrypted H.264 path. Note both are `#[ignore]` by default and so run only when someone asks for them. **Packet-level comparison done 2026-08-08, and it rules out the RTP layer.** Captured both sides through the same SFU (`nix shell nixpkgs#tshark`, with tcpdump inside a container sharing the SFU's network namespace — it runs host networking, so no host privilege was needed). Ours: 518 video packets carrying 500 frames, 500 marker bits, 500 distinct timestamps, header extensions present. A browser publishing H.264 under E2EE through the same SFU: ~2.9 packets per frame, one marker each, extensions present. One marker per frame, monotonic timestamps and extensions are therefore all correct on our side, and the missing-marker theory — the obvious explanation for a receiver reporting `framesReceived: 0` — is dead. **What the capture cannot reach**: the payload is SRTP-encrypted on the wire, so no NAL header is visible in either file. **Root cause identified 2026-08-09, fix written, verification blocked.** Chrome's receive path runs `SpsVuiRewriter::ParseAndRewriteSps(..., kIncoming)` on every incoming SPS and *replaces the payload* when the VUI's bitstream restriction is missing. That happens before the insertable-streams transform. Our AAD is the clear header, which for H.264 spans the SPS (`unencrypted_bytes` returns two bytes into the first slice NAL, so everything before it — SPS and PPS — is inside the authenticated header), and our VAAPI encoder wrote `vui_parameters_present_flag = 0` (`crates/elementium-codec/src/vaapi/h264.rs`). So the worker authenticates an SPS we did not send, AES-GCM fails, every keyframe is dropped, and the receiver counts packets while assembling nothing. Both preconditions were verified in the code before acting. It fits every observation: plain H.264 works (no auth to break), VP8 works (no SPS), browser-to-browser works (libwebrtc's *sender* runs the same rewriter, so the incoming rewrite is a no-op), our own round trip works (no rewriter in the path). **The fix**: the SPS now carries a VUI with the bitstream restriction values libwebrtc treats as needing no change. **Not yet confirmed end to end**, and the reason is not the fix: the `publish_test_tone` harness intermittently stalls while publishing a second track — roughly two runs in three at present, with and without this change, and not in a build from earlier the same day. A browser run against a stalled publisher reports exactly what a failed fix reports, so the one result that would settle this cannot currently be trusted. **Fix the stall first** (see the backlog), then re-run `pnpm exec playwright test -g "H.264 video we encrypt"`, whose `fixme` has been removed. **Hypothesis tested and refuted 2026-08-09: encryption does not disturb the NAL structure.** The idea was that AES-GCM ciphertext, being random, would produce start-code sequences that str0m's packetiser splits on -- emitting extra NALs whose header bytes are ciphertext, which Chrome would discard while our own depacketiser, str0m's symmetric counterpart, concatenated them back and decoded. It fits every observation, and it is wrong. `crates/elementium-webrtc/tests/h264_encrypted_start_codes.rs` encrypts hundreds of realistic Annex B frames, including ones whose clear header ends in the zeros that could form a start code across the join with the separately-escaped body, and finds: the encrypted frame carries exactly the start codes its NALs began with, and str0m splits it into exactly as many packets as the plaintext. The RBSP escaping covers the boundary. **A caution recorded because it nearly produced a false positive**: the first version of that test reported a difference on every frame, and the cause was the fixture -- its filler bytes formed a start code against the header tail, so it was measuring itself. Any future test here must assert its own plaintext contains exactly the three start codes it wrote. **Frame-level comparison done 2026-08-08: our frames and libwebrtc's are the same shape, so the fault is below them.** `ELEMENTIUM_FRAME_DUMP=1` prints the head of every frame at the packetiser boundary, outbound in `write_video` and inbound in `media_data_event`; `subscribe_frame_dump` subscribes to a room and records the inbound side, which recovers what a *browser's* packetiser was given by depacketising it back into frames. Both measured through the same str0m depacketiser, both E2EE on, same SFU:

  - ours:    `00000001 67 42c02896...` (SPS), then `00000001 61 9a...` (non-IDR slices)
  - browser: `00000001 67 42c00c8c...` (SPS), then `00000001 61 e0...` (non-IDR slices)

Identical convention: Annex B, four-byte start codes, same NAL types, livekit's clear slice-header prefix intact in both. So what we hand our packetiser is not the problem, and neither is the frame the E2EE transform produces. **What that leaves**, and it is now the only thing left: str0m's RTP packetisation of that frame versus what Chrome's depacketiser will accept. Our own round trip passes because str0m packetises and str0m depacketises — the two agree with each other and the question was never whether they would. ## Phase 2: Prove the saving

- [X] T004 [US2] **Measured on an OBSBOT Tiny 2 Lite at 1280x720 MJPEG.** Software path: **5.1-5.3ms of process CPU per frame**, 2.28-2.39s over a 15s capture — about 16% of one core, for capture alone. - [X] T005 [US2] **Hardware path: 0.11-0.16ms of process CPU per frame**, 0.05-0.07s over the same 15s — about 0.4% of one core, against 16% for software. Roughly a thirtyfold reduction in capture CPU, and the capture decode timer reads 0.0ms because no CPU decode happens at all. `--hardware` selects it. **What this does not check**: the 37.6% figure was about something wider than the capture stage, and this measures capture only — the hardware path defers the JPEG decode to the GPU at encode time, so neither number includes encoding. The comparison is fair for the stage it covers and should not be quoted for the pipeline.
- [X] T006 [US3] **Confirmed.** On the hardware path the capture decode timer reads `mean_ms=0.0 worst_ms=0.0` across 300 frames and `unusable=0` — there is no CPU decode to fail.
