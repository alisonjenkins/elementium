# Findings from the 2026-08-08 sweep

Four agents audited the project (silent-failure paths, frontend shim gaps, dependencies,
str0m packetisation). What was fixed the same day is listed as done; what remains is here
so it is not rediscovered from scratch.

## Fixed (updated through the night)

- **Choosing a camera or microphone in settings did nothing.** `device_id` was carried from
  the frontend and never read. For cameras the ids could not even be resolved: the picker
  was built from nokhwa's list and capture walks `PipeWire`'s, a different list in a
  different order. Both now come from the enumeration capture actually uses.
- **`getStats()` returned an empty map**, so quality indicators could never work — and
  str0m's ingress and peer stats were being dropped in an unhandled catch-all. Real numbers
  now, with the unavailable ones absent rather than zeroed.
- **Device hotplug was invisible**: `devicechange` was bound to the webview's own
  `navigator.mediaDevices`, which never sees the devices this app uses.
- **Video had no outbound counters at all** — encode errors, undecodable frames and dropped
  sends all vanished, where audio had a whole stats struct for the same bug.
- **Three more silent discards**: outbound media dropped when the publisher task is gone,
  room events with no receiver, and a poisoned enumeration lock reported as "no devices".
- `ashpd` 0.11 -> 0.13 and `aes-gcm` 0.10 -> 0.11. The ashpd runtime path is **unverified**
  — it needs someone to click the portal picker.

## Fixed earlier

- **Hot mic**: `enabled = false` never reached Rust, so muting changed the icon and nothing
  else. Capture now drops muted frames before encoding, and the SFU is told via
  `MuteTrackRequest`. Camera and microphone tracks also finally wire `stop()` to the
  backend, which only the screen share had.
- **Unanswered keyframe requests** are now reported once per episode with a count.
- **Capture logs carry the call's correlation id** and name their track.

## Still open, worth doing

### Silent failures (ranked)

1. `src-tauri/src/commands/media_devices.rs` — `encode_and_send` swallows video encode
   errors, undecodable frames and full-channel drops. Audio got `OutboundAudioStats` for
   exactly this bug; video has no equivalent, so a frozen remote picture has no counter.
2. `crates/elementium-media/src/camera.rs` — `decode_frame_to_rgba` returning `None` is not
   logged at all, while the sibling error branch is. A camera producing undecodable frames
   freezes on its last good one, silently.
3. `src-tauri/src/commands/webrtc.rs` — a poisoned `pipelines` lock in `create_offer` skips
   attaching *every* pipeline and still returns `Ok`: a call joined with no media at all,
   reported as success.
4. `crates/elementium-media/src/pipewire_nodes.rs` — a poisoned lock during enumeration
   returns an empty source list, which the UI shows as "no sources" rather than an error.

### Frontend shim gaps — all closed

1. `replaceTrack` — investigated and left as it is, with a comment saying why. The encoder
   is in Rust and keyed by track identity, and a caller reaches it having already obtained
   the replacement from `getUserMedia`, which restarts that pipeline. The real cause of
   device switching not working was `device_id` being ignored, now fixed.
2. `RTCDataChannel.send()` — implemented, both directions. `send(Blob)` is still refused,
   deliberately and loudly.
3. `getStats()` — real transport statistics, with unavailable fields absent rather than
   zeroed.
4. `restartIce()` — implemented per the DOM's semantics: flag the connection, fire
   `negotiationneeded`, apply the restart to the offer the page then makes.
5. Device hotplug — the shim watches for itself while something is listening.

### Found by the second-pass audit, and closed

- Media bursts could drop a `ConnectionStateChange` from a shared bounded channel, freezing
  the UI's idea of the connection. Control events now have their own path.
- Events arriving before a connection registered its handler were dropped — the worst
  window, since the earliest events are ICE candidates and the first state change.
- A failed E2EE key handover was a `console.warn`. It means the far end hears noise.
- `setLocalDescription()`'s implicit form did nothing; a failed data-channel send raised no
  `error` event.

**The `eval` path is properly escaped** — `serde_json` plus a JSON-argument call shape, no
injection primitive. Recorded because it is worth not re-investigating.

### Dependencies

- `ashpd` 0.11 -> 0.13 touches the screen-capture path directly; worth doing, but it needs
  an attended portal run to verify, so it was not started unattended.
- `aes-gcm` 0.10 -> 0.11 on the E2EE path: no advisory, but worth a deliberate read.
- No production vulnerabilities. The `quick-xml` "high" advisories are build-time only, and
  every frontend advisory is a devDependency.

### H.264 under E2EE (feature 005, T020)

Ruled out this session: RTP headers, the frame handed to the packetiser, and the
packetisation shape itself. What remains is why Chrome's depacketiser rejects a stream its
own SFU parses and our client round-trips. See `specs/005-hardware-video-pipeline/tasks.md`.
