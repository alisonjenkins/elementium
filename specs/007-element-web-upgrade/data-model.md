# Phase 1 data model: Element Web upgrade and patch maintenance

**Created**: 2026-08-08

This feature stores nothing and has no database. It generates two files, and both are read
by a person or a script later, so both have a shape worth fixing now rather than
discovering.

## Entity: Build record

**File**: `element-web-dist/.elementium-build.json`
**Written by**: `scripts/patch-element-web.sh` (T003)
**Read by**: the Tauri startup log (T003), and anyone holding a bug report

Answers "what was actually running", which today costs a round trip to find out.

| Field | Type | Notes |
|---|---|---|
| `elementWebVersion` | string | `v1.12.25`, or the git ref when built from source |
| `source` | `"release"` \| `"git"` | Which path in `fetch-element-web.sh` produced this |
| `sourceRef` | string \| null | Commit SHA when `source` is `git`; null otherwise |
| `builtAt` | string | ISO8601 UTC, e.g. `2026-08-08T09:41:12Z` |
| `patches` | array of `{subject, sha}` | Empty while the patch set is empty. Not optional — an absent field and an empty list mean different things |
| `elementCallFingerprint` | string | Hash over `widgets/element-call/assets` filenames. Element Call is not pinned separately, so this is the only thing that would notice it moving |
| `autojoinInjected` | boolean | **A release build must refuse to proceed when true.** The injection carries a live access token and dials a call on startup |
| `configSource` | string | Which `element-web-config/*.json` was copied |

**Validation**

- Every field is required. A record missing a field is a build whose script was interrupted,
  and should be treated as absent rather than partially trusted.
- `autojoinInjected: true` in a release build is a hard error, not a warning.
- `patches` is `[]`, never absent, when nothing is carried.

**Lifecycle**: written once per patch run, destroyed with `element-web-dist/` on the next
fetch. It describes the tree it sits in and is never merged with a previous one.

## Entity: Patch manifest

**File**: `element-web-patches.md` at the repository root
**Generated by**: `just element-web-rebase` / a manifest task (T019), from the patch branch
**Read by**: anyone asking "what are we carrying, and why"

One row per commit on the patch branch. Generated rather than written, because hand-written
lists of patches stop being true — usually on the day a patch is upstreamed.

| Column | Source | Notes |
|---|---|---|
| Subject | commit subject | |
| SHA | commit sha, short | Against the current rebase base; changes on every rebase, which is expected |
| Intent | commit trailer `Elementium-Intent:` | `upstream-candidate` or `permanent-fork` |
| Why | commit trailer `Elementium-Why:` | One line. The commit body holds the long form |
| Upstream PR | commit trailer `Elementium-Upstream:` | URL, or empty if never offered |
| Status | derived at rebase time | `carried`, `conflicted`, or `dropped-upstream` |

**Why trailers rather than a separate metadata file**: the metadata has to survive a rebase
and stay attached to the commit it describes. A side file has to be kept in step by hand,
and drifts the first time a commit is reordered or amended.

**Validation**

- `Elementium-Intent:` is required on every commit on the patch branch. A commit without one
  has not been classified, and D1 in `plan.md` is the classification.
- `Status: dropped-upstream` is derived from git reporting the commit as already applied
  (research R3), not from the `Elementium-Upstream:` trailer — the trailer says what we
  offered, git says what upstream has.

## Non-entity: the upstream pin

`ELEMENT_WEB_VERSION` in `elementium.config.sh` stays a shell variable rather than becoming
part of either file above. It is an input to the build; the build record is an output of it.
Storing it in one place and reporting it in the other is the point.
